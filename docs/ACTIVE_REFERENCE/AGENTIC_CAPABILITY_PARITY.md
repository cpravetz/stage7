# Agentic Capability Parity Audit

**Status:** Evidence-based audit; implementation proposal, not a redesign decision  
**Scope:** Rebuild proposal, legacy implementation available on `origin/legacy-services-model`, and current checkout  
**Checkout note:** The current checkout contains pre-existing uncommitted changes, including mission orchestration and agent-runtime changes. This audit describes the checked-out code and does not attribute those changes to a particular author or commit.

## Executive finding

The newer rebuild proposal does not direct Stage7 to remove autonomous-agent capabilities. It explicitly calls for stateful actor loops, dynamic assistant runtimes, multi-agent collaboration and delegation, self-correction, and runtime tool generation and deployment.

The implementation is mixed, and has advanced since the initial audit:

- **The mission-agent boundary now has a bounded executing slice.** A mission Agent calls Brain, reads the live system tool catalog, executes tools, can request tool generation, and can delegate bounded subtasks to child Agents. The outer mission phase/task loop is still owned by `MissionOrchestrator`, so this is not yet an open-ended mission-planning actor.
- **Several capabilities were retained in lower-level services.** The current system has Brain model routing, worker-pool LLM/tool-call loops, retries and output refinement, code-execution repair, and a tool-executor fallback that can discover or generate and deploy a code plugin.
- **Recovery and durability have advanced but remain incomplete.** Temporal heartbeats checkpoint the plan, completed task IDs, and completed phases; Agent receipts retain completed-task results. Isolated OS-process acceptance tests verify Agent Runtime receipt recovery and Temporal resume from a persisted task checkpoint without repeating its side effect. Agent execution checkpoints also resume safe task turns after a transient Brain failure, and deterministic child/task identities let a parent recover a completed delegated result from the existing Agent receipt if interrupted before recording that result in its own history. Uncertain non-delegated actions and legacy pending-delegation checkpoints fail closed rather than replaying side effects. A restart of the deployed Docker service during a real mission remains unverified.
- **The existing port-4100 Temporal service is not health-only.** Its mission HTTP API starts, retries, queries, terminates, and directly executes missions inside the existing service; it also scans Artifacts state and resumes eligible in-flight missions. The built-in Artifacts-backed runner is now the default. Connecting to an external Temporal Server is an explicit compatibility choice, not a requirement or a new container.
- **Assistant Skill and mission schedules share one schedule manager.** The existing ToolExecutor `TriggerScheduler` uses the same cron parser, persistence store, tick, schedule listing, enable/disable, and run history for Skill triggers and scheduled mission dispatches to the Stage7 Temporal HTTP API. Scheduled missions use stable occurrence IDs and the Temporal service's Artifacts-backed idempotency check.
- **Assistant Skills and mission-Agent tools remain distinct capability surfaces.** [NEXTGEN_MISSING_SKILLS.md](../NEXTGEN_MISSING_SKILLS.md) is marked as generated and catalogs configuration/input/output schemas for 124 current skill exports; it is not an inventory of missing implementations or evidence that each Skill executes successfully. Assistants own Skills; mission Agents discover and use registered system tools under their own `toolPolicy`.
- **Some legacy/proposal claims were never fully realized or are not demonstrated by the evidence inspected.** In particular, legacy `Step.triggerReflection` is a stub even though the active legacy `ReflectionManager` implements end-of-mission reflection and recovery-plan handling. Neither the proposal nor the inspected code establishes durable learning that improves future agent behavior.

Therefore, the accurate diagnosis is **not “NextGen removed everything” and not “the old system was fully autonomous.”** The first Agent-owned execution/delegation slice is now implemented, while autonomous replanning, complete recovery, and durable mission resumption remain parity gaps. Optional per-Agent tool allowlists are implemented, but legacy Agents without an explicit policy remain unrestricted for compatibility.

## Important corrections to the earlier assessment

1. **The legacy system had more than agent-shaped records.** `Agent` had a running lifecycle loop and explicit sub-agent creation. The older architecture was not merely aspirational on those points.
2. **The legacy system was not uniformly complete.** `Step.triggerReflection` is only a logging stub; active reflection behavior is implemented in `ReflectionManager`. Delegation, recovery, and persistence still require correctness/reliability tests before claiming production parity.
3. **NextGen has genuine agent-adjacent capabilities.** Worker-pool assistants can iterate over tool calls; Brain routes among models; ToolExecutor can repair failed code and generate/deploy code plugins. The key gap is that these services are not consistently capabilities owned and invoked by a mission agent.
4. **The proposal does not explicitly require open-ended, unconstrained agents.** It requires agent-centered dynamic behavior within an enterprise control plane. The intended autonomy should be bounded by tool permissions, tenant isolation, approvals, budgets, iteration limits, and auditability.

## Recommended implementation sequence

This audit is not authorization for a broad rewrite. Use the following gates to restore the architectural boundary incrementally:

### Gate 1 — Agent runtime contract (first slice implemented)

Define an executing `Agent` contract separate from its persisted `AgentDefinition`. The runtime should receive service interfaces for Brain, tool discovery/execution, memory, persistence, delegation, policy, and cancellation. Brain remains a shared service; agents call it when they need reasoning. Temporal may host/supervise durable agent loops, but must not encode every agent decision as a fixed role/task loop.

### Gate 2 — Complete the bounded vertical slice

The current implementation covers Brain/tool execution, live tool discovery, one child-Agent delegation, Temporal plan/task/phase checkpoints, task receipts, safe Agent turn checkpoints, deterministic child/task identity, per-Agent-task execution budgets, and opt-in tool allowlists. Persistence/recreation tests exercise transient Brain retry and recovery of a completed child result when the parent still has a pending delegation. The default policy caps one task at 8 Brain calls, 6 tool/delegation actions, 16,384 total completion tokens, 2,048 tokens per completion, and 2 delegated subtasks; delegations inherit the policy. Planning uses a separate 8,192-token per-completion cap to accommodate complete multi-task plans without weakening validation. These are bounded service limits, not a mission-wide aggregate budget. Agents without an explicit `toolPolicy` remain unrestricted for backwards compatibility; allowlist Agents can use only their configured tool IDs and cannot generate tools.

The isolated acceptance tests cover complementary portions of this bounded mission: Agent Runtime process restart with local Mongo and deterministic Brain/ToolExecutor endpoints; and Temporal OS-process restart with an isolated Artifacts fixture and a persisted task side effect. They verify tool allowlist denial, recovery from a tool error, child delegation, receipt reuse, scoped learning retrieval, checkpoint resume, and lease contention.

**The bounded deployed mission gate is now complete** for `agentic-parity-live-20261015-02`. In the running direct-mode stack, mission-scoped Agents used Brain and the live tool path to calculate `31*37 = 1147`, delegate `29*41 = 1189` to a child Agent, record a policy-denied `search_web` attempt, recover from a failed `calculate("2*")` with `calculate("2+2") = 4`, and use the two persisted multiplication outputs to calculate `1147-1189 = -42`. The persisted plan and mission-review report show all six phases and tasks completed and verify the operand task IDs. Agent Runtime also logged a successful complaint submission after a Brain response returned empty content and failed output validation.

After a Temporal container redeploy, a retry resumed from the persisted six completed tasks and completed the mission review without replaying task actions. This verifies recovery from persisted mission checkpoints across a service redeploy, not interruption during an in-flight Agent action. Generated-tool creation/use under mission policy and recovery from a process crash during an active action remain separate acceptance gates.

### Gate 3 — Harden extension and optimization

Generated plugins use the existing `CodeExecutor` contract, matching locally authored code tools: a child process with timeout and output limits, but no additional restrictions on environment variables, credentials, filesystem access, network, or subprocesses. This preserves the capabilities intended for local code generation; it is not a security boundary for hostile or untrusted source. Review plugin behavior and schemas before registration, and demonstrate explicit per-Agent policy behavior end to end before treating runtime code generation as production-ready. If Stage7 later runs untrusted generated code across tenants, design a separate isolation policy without silently constraining the local-tool contract. Connect task requirements and measured outcomes to Brain routing. Define “learning” as an explicit, auditable data flow before implementing it.

### Gate 4 — Update claims from demonstrated behavior

For every capability, require observed end-to-end execution and an observable trace; automated tests are regression aids, not proof that deployed behavior works. Then update the README and [user guide](../USER_GUIDE.md) to distinguish currently available behavior from roadmap or design intent.

Direct-mode mission Pause and Stop are cooperative: the active Agent task is allowed to finish and persist before control is applied at the next task checkpoint. Persisted paused missions remain paused across restarts. ### AgentExecutor checkpoint resume rescue (2026-10-15)

A code-level fix to `AgentExecutor.ts` addresses the primary blocker for the `agentic-plugin-create-20261102-03` creator mission. The `grantResumeAllowance` flag previously required `retryGuidance` to be truthy before granting the bounded continuation budget (`RESUME_BRAIN_CALL_BONUS` = 4 extra Brain calls). When a mission is retried through the Temporal retry endpoint without explicit `retryPrompt` or `userGuidance`, `retryGuidance` is an empty string (falsy), so the agent received no extra Brain calls on retry. If the persisted `AgentExecutionCheckpoint` had already consumed its full `maxBrainCalls` budget (8), the executor's resume loop did not execute and the task failed immediately with "exceeded Brain budget," preventing the agent from producing the required `plugin_creation_result` and `plugin_verification_result` artifact sections.

**Fix:** `grantResumeAllowance` now depends only on the presence of a checkpoint and the absence of the `RESUME_BUDGET_MARKER` in history. This grants a single bounded continuation budget whenever an agent resumes from a persisted checkpoint, regardless of whether explicit user retry guidance is provided.

**Supporting changes:**
- `expectedArtifactCorrection` now references action results already in the conversation, guiding the agent to use completed action receipts when populating required artifact sections.
- The `alreadySatisfiedRequiredAction` correction message now explicitly references the existing action result in the conversation history.

**Tests:** One new test "grants a resume allowance without retry guidance when brain calls are exhausted" verifies that an agent resuming with `brainCalls: 8` and no `retryGuidance` receives the 4-call continuation budget and successfully completes. All 36 AgentExecutor tests pass.

**Note:** This fix addresses the code-level blocker that prevented the creator mission from completing during retry. A live re-run of `agentic-plugin-create-20261102-03` (or a new equivalent) is required to verify end-to-end mission completion. The Brain latency-ranking change in `ModelRouter.ts` (formula `80 / (1 + avgLatencyMs / 30000) - 40`, range -40..+40) is already implemented and covered by 17 routing tests but remains undeployed at this checkpoint.

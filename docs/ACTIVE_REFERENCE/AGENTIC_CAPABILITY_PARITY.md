# Agentic Capability Parity Audit

**Status:** Evidence-based audit; implementation proposal, not a redesign decision  
**Scope:** Rebuild proposal, legacy implementation available on `origin/legacy-services-model`, and current checkout  
**Checkout note:** The current checkout contains pre-existing uncommitted changes, including mission orchestration and agent-runtime changes. This audit describes the checked-out code and does not attribute those changes to a particular author or commit.

## Executive finding

The newer rebuild proposal does not direct Stage7 to remove autonomous-agent capabilities. It explicitly calls for stateful actor loops, dynamic assistant runtimes, multi-agent collaboration and delegation, self-correction, and runtime tool generation and deployment.

The implementation is mixed, and has advanced since the initial audit:

- **The mission-agent boundary now has a bounded executing slice.** A mission Agent calls Brain, reads the live system tool catalog, executes tools, can request tool generation, and can delegate bounded subtasks to child Agents. The outer mission phase/task loop is still owned by `MissionOrchestrator`, so this is not yet an open-ended mission-planning actor.
- **Several capabilities were retained in lower-level services.** The current system has Brain model routing, worker-pool LLM/tool-call loops, retries and output refinement, code-execution repair, and a tool-executor fallback that can discover or generate and deploy a code plugin.
- **Recovery and durability have advanced but remain incomplete.** Temporal heartbeats checkpoint the plan, completed task IDs, and completed phases; Agent receipts retain completed-task results. Isolated OS-process acceptance tests verify Agent Runtime receipt recovery and Temporal resume from a persisted task checkpoint without repeating its side effect. Agent execution checkpoints also resume safe task turns after a transient Brain failure, and deterministic child/task identities let a parent recover a completed delegated result from the existing Agent receipt if interrupted before recording that result in its own history. Uncertain non-delegated actions and legacy pending-delegation checkpoints fail closed rather than replaying side effects. A restart of the deployed Docker service during a real mission remains unverified.
- **The existing port-4100 Temporal service is not health-only.** Its mission HTTP API starts, retries, queries, terminates, and directly executes missions inside the existing service; it also scans Artifacts state and resumes eligible in-flight missions. The built-in Artifacts-backed runner is now the default. Connecting to an external Temporal Server is an explicit compatibility choice, not a requirement or a new container.
- **Assistant Skill and mission schedules share one schedule manager.** The existing ToolExecutor `TriggerScheduler` uses the same cron parser, persistence store, tick, schedule listing, enable/disable, and run history for Skill triggers and scheduled mission dispatches to the Stage7 Temporal HTTP API. Scheduled missions use stable occurrence IDs and the Temporal service's Artifacts-backed idempotency check.
- **Assistant Skills and mission-Agent tools remain distinct capability surfaces.** [NEXTGEN_MISSING_SKILLS.md](../NEXTGEN_MISSING_SKILLS.md) is marked as generated and catalogs configuration/input/output schemas for 124 current skill exports; it is not an inventory of missing implementations or evidence that each Skill executes successfully. Assistants own Skills; mission Agents discover and use registered system tools under their own `toolPolicy`.
- **Some legacy/proposal claims were never fully realized or are not demonstrated by the evidence inspected.** In particular, legacy `Step.triggerReflection` is a stub even though the active legacy `ReflectionManager` implements end-of-mission reflection and recovery-plan handling. Neither the proposal nor the inspected code establishes durable learning that improves future agent behavior.

Therefore, the accurate diagnosis is **not “NextGen removed everything” and not “the old system was fully autonomous.”** The first Agent-owned execution/delegation slice is now implemented, while autonomous replanning, complete recovery, and durable mission resumption remain parity gaps. Optional per-Agent tool allowlists are implemented, but legacy Agents without an explicit policy remain unrestricted for compatibility.

## Important corrections to the earlier assessment

1. **The legacy system had more than agent-shaped records.** `Agent` had a running lifecycle loop and explicit sub-agent creation. The older architecture was not merely aspirational on those points.
2. **The legacy system was not uniformly complete.** `Step.triggerReflection` is only a logging stub; active reflection behavior is implemented in `ReflectionManager`. Delegation, recovery, and persistence still require correctness/reliability tests before claiming production parity.
3. **NextGen has genuine agent-adjacent capabilities.** Worker-pool assistants can iterate over tool calls; Brain routes among models; ToolExecutor can repair failed code and generate/deploy code plugins. The key gap is that these services are not consistently capabilities owned and invoked by a mission agent.
4. **The proposal does not explicitly require open-ended, unconstrained agents.** It requires agent-centered dynamic behavior within an enterprise control plane. The intended autonomy should be bounded by tool permissions, tenant isolation, approvals, budgets, iteration limits, and auditability.

## Recommended implementation sequence

This audit is not authorization for a broad rewrite. Use the following gates to restore the architectural boundary incrementally:

### Gate 1 — Agent runtime contract (first slice implemented)

Define an executing `Agent` contract separate from its persisted `AgentDefinition`. The runtime should receive service interfaces for Brain, tool discovery/execution, memory, persistence, delegation, policy, and cancellation. Brain remains a shared service; agents call it when they need reasoning. Temporal may host/supervise durable agent loops, but must not encode every agent decision as a fixed role/task loop.

### Gate 2 — Complete the bounded vertical slice

The current implementation covers Brain/tool execution, live tool discovery, one child-Agent delegation, Temporal plan/task/phase checkpoints, task receipts, safe Agent turn checkpoints, deterministic child/task identity, per-Agent-task execution budgets, and opt-in tool allowlists. Persistence/recreation tests exercise transient Brain retry and recovery of a completed child result when the parent still has a pending delegation. The default policy caps one task at 8 Brain calls, 6 tool/delegation actions, 16,384 total completion tokens, 2,048 tokens per completion, and 2 delegated subtasks; delegations inherit the policy. Planning uses a separate 4,096-token per-completion cap. These are bounded service limits, not a mission-wide aggregate budget. Agents without an explicit `toolPolicy` remain unrestricted for backwards compatibility; allowlist Agents can use only their configured tool IDs and cannot generate tools.

The isolated acceptance tests now cover complementary portions of this bounded mission: Agent Runtime process restart with local Mongo and deterministic Brain/ToolExecutor endpoints; and Temporal OS-process restart with an isolated Artifacts fixture and a persisted task side effect. The tests verify tool allowlist denial, recovery from a tool error, child delegation, receipt reuse, scoped learning retrieval, checkpoint resume, and lease contention. They do not yet constitute one deployed-stack trace through the real Brain, ToolExecutor, Agent Runtime, Artifacts, and Temporal services.

Still complete and verify one bounded mission in the running stack in which an agent:

1. receives a goal and policy/tool budget;
2. reasons through Brain and selects from its permitted tools;
3. delegates one subtask to a dynamically registered child agent;
4. consumes the child result and completes the goal;
5. recovers from an injected tool failure or escalates explicitly; and
6. resumes after a worker restart without duplicating completed side effects.

The test must inspect runtime calls, persisted state, tool permissions, and final output—not just agent records or UI events.

### Gate 3 — Harden extension and optimization

Generated plugins use the existing `CodeExecutor` contract, matching locally authored code tools: a child process with timeout and output limits, but no additional restrictions on environment variables, credentials, filesystem access, network, or subprocesses. This preserves the capabilities intended for local code generation; it is not a security boundary for hostile or untrusted source. Review plugin behavior and schemas before registration, and demonstrate explicit per-Agent policy behavior end to end before treating runtime code generation as production-ready. If Stage7 later runs untrusted generated code across tenants, design a separate isolation policy without silently constraining the local-tool contract. Connect task requirements and measured outcomes to Brain routing. Define “learning” as an explicit, auditable data flow before implementing it.

### Gate 4 — Update claims from demonstrated behavior

For every capability, require observed end-to-end execution and an observable trace; automated tests are regression aids, not proof that deployed behavior works. Then update the README and [user guide](../USER_GUIDE.md) to distinguish currently available behavior from roadmap or design intent.

## Current status and next action

The port-4100 Stage7 Temporal service is the mission HTTP API and built-in workflow runner, not a health-only shim. `TEMPORAL_BACKEND=direct` is the default; it supervises missions in the existing service, uses Artifacts and Agent Runtime checkpoints, coordinates recovery with leases, and rescans persisted running missions. The optional Temporal Server backend is only selected by setting `TEMPORAL_BACKEND=temporal-server`; no external Temporal Server or additional container is required for the default path. Isolated Temporal and Agent Runtime OS-process restart acceptances pass, and Mongo lease semantics pass against local Mongo. A Docker service restart during a real mission and cross-service mission acceptance remain outstanding.

Direct-mode mission Pause and Stop are cooperative: the active Agent task is allowed to finish and persist before control is applied at the next task checkpoint. Persisted paused missions remain paused across restarts. If a process exits while a pause or termination is pending, recovery claims the mission lease and records the paused/canceled state without replaying an uncertain in-flight task. This does not restore the interrupted Agent's in-progress reasoning or tool loop. The optional Temporal Server backend does not support cooperative pause/resume; its termination path uses native immediate termination.

Assistant Skill schedules and scheduled missions now share ToolExecutor's existing `TriggerScheduler`: one cron parser, persistence store, polling timer, schedule list, and enable/disable management. Skill runs use ToolExecutor and preserve their normal approval gates. Mission schedules dispatch through the existing Temporal HTTP API, use deterministic IDs per cron occurrence, and require Artifacts persistence for durable schedule records. The old `watches` polling path remains separate from these cron schedules.

Mission plan generation, dependency-aware within-phase task selection, task execution, phase review/amendment, and completion review use mission-scoped Agents through Agent Runtime and Brain. Mission Agents do not receive Assistant identity or execute through Worker Pool; they call the shared Brain service via Agent Runtime. Direct-mode recovery rebuilds checkpoints from Artifacts plans and reuses Agent receipts. Mongo leases and isolated OS-process restart paths are covered, but a Docker service restart during a real mission remains outstanding; uncertain actions without a safe checkpoint and legacy v1 pending-action checkpoints fail closed. The mission director chooses among ready tasks in the persisted plan; a phase reviewer can append one focused follow-up task at a time until the phase goal is satisfied or no actionable follow-up is returned. There is no fixed amendment-count or amended-phase task-count ceiling, and completed work cannot be rewritten. Mission metadata accepts an `agentToolPolicies` object keyed by role (or `"*"`) with `{ "mode": "allowlist", "tools": ["registered_tool_id"] }` or `{ "mode": "all" }`; unspecified roles remain unrestricted for compatibility, and restricted Agents cannot generate tools. The Agent Runtime rejects cross-mission Agent/task access through mission-scoped routes, and its executor has a bounded Brain request timeout plus one safe persisted-checkpoint retry. Focused tests cover policy provisioning, cross-mission access denial, timeout, and same-task retry; the Mongo-backed Agent Runtime restart acceptance and Temporal process-restart acceptance pass. A focused AgentExecutor regression demonstrates registered generated-tool execution with an allowlist, but useful execution and policy denial in a deployed mission remain open. Generated plugins retain the local CodeExecutor capabilities and are not isolated from ToolExecutor. Scoped learning retrieval persists across Agent Runtime restarts and excludes other tenants; measured behavior change and independent provenance validation remain open. The remaining implementation/evidence gaps are a single deployed mission trace covering delegation, repair/escalation, explicit policy, generated tools, and process recovery; deployed Brain adaptation evidence; and independently authenticated learning provenance. Preserve Brain and ToolExecutor as shared services; keep Agents as mission-scoped actors and Temporal as the durable supervisor.

Live evaluation of `mission-mission-1791917727962` exposed a planner convergence defect: the first three Brain responses each proposed eight tasks in one phase, while the fourth planner task hit the 120-second Brain timeout. That run failed without a persisted plan or worker execution. Planner prompts and validation now impose no upper limit on phases per plan or tasks per phase; a non-clarification plan must still contain at least one phase, and every phase at least one task. Focused tests verify one phase with eight tasks and a plan with nine phases are accepted.

The fresh corrected-prompt run, `mission-mission-1791919183657`, preserved the requested `$35,000-$50,000` revenue and `$15,000` gross-margin targets. Planning persisted four phases with task counts `2, 1, 2, 2`, but the run failed after two amendments under the then-deployed amendment cap. The next uncapped test, `mission-mission-1791920665773`, appended five amendments, proving the fixed ceiling was gone. Its Agent outputs repeatedly described plans and tool lists rather than producing the requested business idea, so the test was stopped and marked canceled after the task completed. That trace exposed that each task's `systemPrompt` was not included in its execution prompt. The runtime now includes task-specific instructions and treats a repeated title, description, and expected-artifact set as non-actionable rather than relying on an amendment count. The updated-image rerun, `mission-mission-1791921381609`, persisted a five-phase plan and executed two review amendments, then failed because no actionable follow-up was available while the phase goal remained unmet; no numeric ceiling was reached. Later phases did not start. Amendment convergence is unbounded by count, but live mission quality remains an open gate.

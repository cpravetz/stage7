# Agentic Capability Parity Audit

**Status:** Evidence-based audit; implementation proposal, not a redesign decision  
**Scope:** Rebuild proposal, legacy implementation available on `origin/legacy-services-model`, and current checkout  
**Checkout note:** The current checkout contains pre-existing uncommitted changes, including mission orchestration and agent-runtime changes. This audit describes the checked-out code and does not attribute those changes to a particular author or commit.

## Executive finding

The newer rebuild proposal does not direct Stage7 to remove autonomous-agent capabilities. It explicitly calls for stateful actor loops, dynamic assistant runtimes, multi-agent collaboration and delegation, self-correction, and runtime tool generation and deployment.

The implementation is mixed, and has advanced since the initial audit:

- **The mission-agent boundary now has a bounded executing slice.** A mission Agent calls Brain, reads the live system tool catalog, executes tools, can request tool generation, and can delegate bounded subtasks to child Agents. The outer mission phase/task loop is still owned by `MissionOrchestrator`, so this is not yet an open-ended mission-planning actor.
- **Several capabilities were retained in lower-level services.** The current system has Brain model routing, worker-pool LLM/tool-call loops, retries and output refinement, code-execution repair, and a tool-executor fallback that can discover or generate and deploy a code plugin.
- **Recovery and durability have advanced but remain incomplete.** Temporal heartbeats checkpoint the plan, completed task IDs, and completed phases; Agent receipts retain completed-task results. Agent execution checkpoints now resume safe task turns after a transient Brain failure, and deterministic child/task identities let a parent recover a completed delegated result from the existing Agent receipt if interrupted before recording that result in its own history. Uncertain non-delegated actions and legacy pending-delegation checkpoints fail closed rather than replaying side effects. Actual service/process restart recovery remains unverified.
- **The existing port-4100 Temporal service is not health-only.** Its mission HTTP API starts, retries, queries, terminates, and directly executes missions inside the existing service; it also scans Artifacts state and resumes eligible in-flight missions. The built-in Artifacts-backed runner is now the default. Connecting to an external Temporal Server is an explicit compatibility choice, not a requirement or a new container.
- **Assistant Skill and mission schedules share one schedule manager.** The existing ToolExecutor `TriggerScheduler` uses the same cron parser, persistence store, tick, schedule listing, enable/disable, and run history for Skill triggers and scheduled mission dispatches to the Stage7 Temporal HTTP API. Scheduled missions use stable occurrence IDs and the Temporal service's Artifacts-backed idempotency check.
- **Some legacy/proposal claims were never fully realized or are not demonstrated by the evidence inspected.** In particular, legacy `Step.triggerReflection` is a stub even though the active legacy `ReflectionManager` implements end-of-mission reflection and recovery-plan handling. Neither the proposal nor the inspected code establishes durable learning that improves future agent behavior.

Therefore, the accurate diagnosis is **not “NextGen removed everything” and not “the old system was fully autonomous.”** The first Agent-owned execution/delegation slice is now implemented, while autonomous replanning, complete recovery, and durable mission resumption remain parity gaps. Optional per-Agent tool allowlists are implemented, but legacy Agents without an explicit policy remain unrestricted for compatibility.

## Important corrections to the earlier assessment

1. **The legacy system had more than agent-shaped records.** `Agent` had a running lifecycle loop and explicit sub-agent creation. The older architecture was not merely aspirational on those points.
2. **The legacy system was not uniformly complete.** `Step.triggerReflection` is only a logging stub; active reflection behavior is implemented in `ReflectionManager`. Delegation, recovery, and persistence still require correctness/reliability tests before claiming production parity.
3. **NextGen has genuine agent-adjacent capabilities.** Worker-pool assistants can iterate over tool calls; Brain routes among models; ToolExecutor can repair failed code and generate/deploy code plugins. The key gap is that these services are not consistently capabilities owned and invoked by a mission agent.
4. **The proposal does not explicitly require open-ended, unconstrained agents.** It requires agent-centered dynamic behavior within an enterprise control plane. The intended autonomy should be bounded by tool permissions, tenant isolation, approvals, budgets, iteration limits, and auditability.

## Recommended implementation sequence

This audit is not authorization for a broad rewrite. Use the following gates to restore the architectural boundary incrementally:

### Gate 1 — Agent runtime contract (first slice implemented)

Define an executing `Agent` contract separate from its persisted `AgentDefinition`. The runtime should receive service interfaces for Brain, tool discovery/execution, memory, persistence, delegation, policy, and cancellation. Brain remains a shared service; agents call it when they need reasoning. Temporal may host/supervise durable agent loops, but must not encode every agent decision as a fixed role/task loop.

### Gate 2 — Complete the bounded vertical slice

The current implementation covers Brain/tool execution, live tool discovery, one child-Agent delegation, Temporal plan/task/phase checkpoints, task receipts, safe Agent turn checkpoints, deterministic child/task identity, per-Agent-task execution budgets, and opt-in tool allowlists. Persistence/recreation tests exercise transient Brain retry and recovery of a completed child result when the parent still has a pending delegation. The default policy caps one task at 8 Brain calls, 6 tool/delegation actions, 16,384 total completion tokens, 2,048 tokens per completion, and 2 delegated subtasks; delegations inherit the policy. Planning uses a separate 4,096-token per-completion cap. These are bounded service limits, not a mission-wide aggregate budget. Agents without an explicit `toolPolicy` remain unrestricted for backwards compatibility; allowlist Agents can use only their configured tool IDs and cannot generate tools.

Still complete and verify one bounded mission in which an agent:

1. receives a goal and policy/tool budget;
2. reasons through Brain and selects from its permitted tools;
3. delegates one subtask to a dynamically registered child agent;
4. consumes the child result and completes the goal;
5. recovers from an injected tool failure or escalates explicitly; and
6. resumes after a worker restart without duplicating completed side effects.

The test must inspect runtime calls, persisted state, tool permissions, and final output—not just agent records or UI events.

### Gate 3 — Harden extension and optimization

Generated JavaScript runs with the Node Permission Model: its environment is allowlisted, filesystem access is confined to its temporary directory, and child processes are disabled. Outbound HTTP is still allowed and is not host-restricted; this is a constrained process profile, not a complete isolation boundary or a source-code safety proof. Generated Python fails closed until an equivalent restricted profile exists. Still review plugin behavior and schemas before registration, establish network egress policy, and demonstrate explicit per-Agent policy behavior end to end before treating runtime code generation as production-ready. Connect task requirements and measured outcomes to Brain routing. Define “learning” as an explicit, auditable data flow before implementing it.

### Gate 4 — Update claims from demonstrated behavior

For every capability, require observed end-to-end execution and an observable trace; automated tests are regression aids, not proof that deployed behavior works. Then update the README and [user guide](../USER_GUIDE.md) to distinguish currently available behavior from roadmap or design intent.

## Current status and next action

The port-4100 Stage7 Temporal service is the mission HTTP API and built-in workflow runner, not a health-only shim. `TEMPORAL_BACKEND=direct` is the default; it executes through `MissionOrchestrator` in the existing service, uses Artifacts and Agent Runtime checkpoints, coordinates recovery with leases, and rescans persisted running missions. The optional Temporal Server backend is only selected by setting `TEMPORAL_BACKEND=temporal-server`; no external Temporal Server or additional container is required for the default path. Live restart and Mongo integration tests remain outstanding.

Assistant Skill schedules and scheduled missions now share ToolExecutor's existing `TriggerScheduler`: one cron parser, persistence store, polling timer, schedule list, and enable/disable management. Skill runs use ToolExecutor and preserve their normal approval gates. Mission schedules dispatch through the existing Temporal HTTP API, use deterministic IDs per cron occurrence, and require Artifacts persistence for durable schedule records. The old `watches` polling path remains separate from these cron schedules.

Mission plan generation, dependency-aware within-phase task selection, task execution, phase review/amendment, and completion review use mission-scoped Agents through Agent Runtime and Brain. Mission Agents do not receive Assistant identity, execute through Worker Pool, or call Brain directly from Temporal; completed-task receipts still protect retries. Direct-mode recovery and retry rebuild completed-task checkpoints from Artifacts plans and reuse Agent receipts. Lease expiry and mocked cross-client contention are unit-tested, but Mongo integration and actual process-restart behavior remain unverified. Agent Runtime persistence/recreation tests verify safe continuation after transient Brain failure and idempotent recovery of a completed delegated child; uncertain actions without a safe checkpoint and legacy v1 pending-action checkpoints remain fail-closed. The mission director may choose only among ready tasks in the persisted plan; a phase reviewer can append at most two follow-up tasks before approval, but cannot rewrite completed work or amend after approval. Optional per-Agent allowlists filter both the tools shown to Brain and the tools that can execute; delegated Agents inherit the parent's policy. The default remains unrestricted for backward compatibility, and restricted Agents cannot generate tools. Generated JavaScript is marked and executed in a restricted Node Permission Model process (clean environment, temporary-directory-only filesystem access, and no child processes); outbound HTTP remains unrestricted. Generated Python fails closed. This is not source-code review or network-egress isolation, and live operational behavior remains unverified. Gate 2 remains open until a running stack demonstrates delegation, repair or explicit escalation, and process-restart recovery without duplicate completed side effects. Memory-backed behavior change and learning remain undefined/unverified. Next: demonstrate restricted generated-tool execution and explicit per-Agent policy behavior in a running mission, then complete the controlled process-restart acceptance test. Preserve Brain and ToolExecutor as shared services; keep Agents as mission-scoped actors and Assistants as persistent domain collaborators.
